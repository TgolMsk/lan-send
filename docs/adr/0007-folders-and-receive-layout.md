# 0007. 文件夹传输与接收目录布局

- 状态：已接受
- 日期：2026-09-07

## 背景

里程碑 2 要发送多文件与文件夹、按设备/日期/类型归类接收、处理同名冲突。官方 1.9 起 `fileName` 可含 `/` 分隔的相对路径，接收端会按路径建目录；用户已决定不做 zip 回退。

## 决策

1. 新增核心模块 `transfer`：`outgoing` 把本地路径变成待发文件列表，`incoming` 决定收到的文件放哪。它们不依赖网络层，可单独测试。
2. **发送端收集**：命令行给出的路径本身跟随符号链接（用户指的就是目标），目录内部的符号链接一律跳过并记录；隐藏文件（名字以 `.` 开头，Windows 上另看隐藏属性）默认跳过，可关；`.app`、`.lnk` 当普通目录/文件；空目录无法表达，忽略。相对名为 `<顶层目录名>/<相对路径>`，始终用 `/`。发送前给出文件数、总大小与跳过项。
3. **接收端布局**：`<接收目录>[/<发送方别名>][/<YYYY-MM-DD>][/<Images|Videos|Audio|Documents|Other>]/<净化后的相对路径>`。三条规则默认全关，可独立开启，顺序固定。类型按 MIME 前缀判断，文档类另含 pdf、office、文本。
4. **同名冲突**：`rename`（默认，`name (n).ext`）、`overwrite`、`ask`。`ask` 由应用层向用户提问，无人值守的 CLI（`--auto-accept`）退化为 `rename`。同一会话内已分配的路径也算占用。
5. 最终路径必须位于接收目录内，检查在建目录之前做。

## 备选方案

- 文件夹打成 zip：对方是官方客户端时才需要，而官方已支持路径，用户否决。
- 类型目录名本地化：文件夹名进入文件系统后不宜随语言变化，用英文固定名。

## 后果

- 发送文件夹时文件数可能很大，`prepare-upload` 的 JSON 会变大，服务端上限已放宽到 32 MB。
- 归类目录只影响接收端，发送端不感知。
